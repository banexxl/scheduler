# Appointment Notifications Foundation

**Milestone 6.12**

## Overview

Transactional email notifications for appointment creation, rescheduling, and cancellation using an outbox pattern. Notifications are asynchronous — appointment mutations never wait for the email provider.

## Architecture: Outbox Pattern

```
Appointment Mutation
        │
        ▼
┌──────────────────────┐
│ Enqueue to outbox    │ ← Same logical flow, after appointment success
│ (template snapshot)  │
└──────────────────────┘
        │
        ▼
┌──────────────────────┐
│ notification_outbox  │ ← Database record: pending
└──────────────────────┘
        │
        ▼  (external cron / protected route)
┌──────────────────────┐
│ Process batch        │ ← claim_notification_outbox_batch (SKIP LOCKED)
│ Send via provider    │
│ Record delivery      │
└──────────────────────┘
```

**Why outbox?**

- Appointment mutations remain fast and reliable regardless of provider status.
- Provider temporary failures are retried without losing the notification.
- Notifications are immutable once enqueued (snapshot policy).
- Multiple workers can process concurrently without duplicates.

## Rendering and Escaping

- All injected values are HTML-escaped before insertion into the body.
- Subject line uses plain-text values (no HTML escaping needed for email headers).
- A plain-text version is auto-generated by stripping HTML tags.
- No `eval`, dynamic code execution, or unrestricted expression engines are used.
- Templates use simple `{{variable}}` substitution only.

## Snapshot Policy

Templates are rendered **at enqueue time**. The outbox stores:

- `rendered_subject` — Final subject line
- `rendered_html` — Final HTML body
- `rendered_text` — Final plain-text body
- `sender_name` — Resolved sender identity
- `reply_to_email` — Resolved reply-to address

**Benefits:**

- Outbox records are immutable after creation.
- Retries send identical content.
- Template edits do not alter already-enqueued notifications.
- Processing workers do not need to reload business data.

## Outbox Statuses

| Status | Meaning |
|--------|---------|
| `pending` | Waiting for processing or retry |
| `processing` | Claimed by a worker |
| `sent` | Provider accepted the message |
| `failed` | No more automatic retries |
| `cancelled` | Intentionally suppressed |

**Important:** `sent` means provider acceptance only. It does NOT guarantee inbox delivery. Provider delivery webhooks (bounce, delivered, opened) are out of scope.

## Idempotency Keys

Deterministic keys prevent duplicate notifications:

- Created: `appointment:{id}:created`
- Cancelled: `appointment:{id}:cancelled`
- Rescheduled: `appointment:{id}:rescheduled:{updatedAt}`

Rescheduled uses `updatedAt` because the same appointment may be rescheduled multiple times, each generating a legitimate notification.

## Claiming and Row Locking

The `claim_notification_outbox_batch` RPC:

1. Recovers stale locks older than 10 minutes.
2. Selects pending rows where `next_attempt_at <= now()`.
3. Uses `FOR UPDATE SKIP LOCKED` for concurrency safety.
4. Sets status to `processing`, locks the row with worker ID.
5. Limits batch size (max 50).

Multiple workers can run simultaneously without processing the same row.

## Retry Policy

| Attempt | Delay After Failure |
|---------|---------------------|
| 1 | Immediate |
| 2 | 1 minute + jitter |
| 3 | 5 minutes + jitter |
| 4 | 30 minutes + jitter |
| 5 | 2 hours + jitter |

After attempt 5: status = `failed` (terminal).

Non-retryable errors (invalid recipient, validation errors) fail immediately.

## Delivery Tracking

Each send attempt creates a `notification_deliveries` record:

- Provider name
- Provider message ID (if successful)
- Attempt number
- Status (processing/sent/failed)
- Safe error code and message
- Timestamps

Provider response metadata is sanitized — no API keys, auth headers, or full request bodies stored.

## Provider Abstraction

```typescript
interface EmailProvider {
  send(input: SendEmailInput): Promise<SendEmailResult>;
}
```

### Console Provider (development)

- Does not send externally
- Logs safe metadata (not full body)
- Returns synthetic message ID
- Always "configured"

### Nodemailer Provider (production)

- Uses SMTP transport via Nodemailer
- Configurable host, port, auth credentials
- Connection/greeting/socket timeouts (10s/10s/15s)
- Maps SMTP errors to retryable (timeouts, connection) vs non-retryable (invalid recipient, rejected)
- Requires `SMTP_HOST`, `NOTIFICATION_FROM_EMAIL`, and optionally `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`

## Sender and Reply-To Behavior

```
From: {NOTIFICATION_FROM_EMAIL}       ← Platform-level, verified sender
From-Name: {tenant sender_name}       ← Tenant-configurable display name
Reply-To: {tenant reply_to_email}     ← Tenant-configurable, optional
```

Tenants cannot set arbitrary `From` addresses. Only the display name and reply-to are configurable.

## Appointment Integration

### Creation (internal + public booking)

After successful appointment insert:
- Enqueues `appointment_created` notification
- Skips if: no customer email, notifications disabled, confirmation disabled
- Non-blocking: appointment creation succeeds regardless of enqueue result

### Rescheduling

After successful reschedule:
- Enqueues `appointment_rescheduled` only when scheduling fields changed
- Scheduling fields: starts_at, ends_at, service, location, resource
- Customer-detail-only edits do NOT trigger notification
- Includes previous timestamps in payload

### Cancellation

After successful cancellation:
- Enqueues `appointment_cancelled`
- Includes safe cancellation reason
- Idempotency prevents duplicate: cancelling an already-cancelled appointment does not re-enqueue

## Public Booking Confirmation

The confirmation page conditionally displays:

> A confirmation email will be sent to the address provided.

Only when:
- Customer email exists
- Notifications are enabled
- Booking confirmation is enabled
- Outbox enqueue succeeded

Does not claim email was delivered — only that it was enqueued.

## Failure Behavior

- Provider failure never rolls back appointment mutations
- Provider failure never exposes stack traces to users
- Retryable errors are automatically retried per policy
- Terminal errors are marked `failed` with safe error message
- Manual retry available for owners/admins via appointment detail page

## RLS and Security

| Table | SELECT | INSERT/UPDATE/DELETE |
|-------|--------|---------------------|
| `tenant_notification_settings` | All active members | Owner/admin only |
| `notification_templates` | All active members | Owner/admin only |
| `notification_outbox` | Owner/admin only | Via SECURITY DEFINER RPCs |
| `notification_deliveries` | Owner/admin only | Via SECURITY DEFINER RPCs |

- Public booking users have no access to notification tables.
- Processing route requires `NOTIFICATION_PROCESSOR_SECRET` Bearer token.
- Recipient emails are partially masked in admin list views.

## Processing Route

```
POST /api/internal/notifications/process
Authorization: Bearer {NOTIFICATION_PROCESSOR_SECRET}
```

Query parameters:
- `batchSize` (optional, default: 10, max: 50)

Response (safe diagnostics):
```json
{
  "processed": 5,
  "sent": 4,
  "failed": 1,
  "retrying": 0,
  "results": [{ "outboxId": "...", "status": "sent", "errorCode": null }]
}
```

No recipient addresses exposed in response.

## Required Cron Configuration

The processing route must be called periodically by an external scheduler:

```
POST /api/internal/notifications/process
Authorization: Bearer {NOTIFICATION_PROCESSOR_SECRET}
```

Suggested frequency: every 1–2 minutes.

Platform options: Vercel Cron, Railway Cron, external cron service, or manual trigger for development.

**Automatic processing is NOT active unless a cron job is configured.**

| Variable | Required | Description |
|----------|----------|-------------|
| `EMAIL_PROVIDER` | No | `console` (default) or `nodemailer` |
| `NOTIFICATION_FROM_EMAIL` | For nodemailer | Sender email address |
| `SMTP_HOST` | For nodemailer | SMTP server hostname |
| `SMTP_PORT` | No | SMTP port (default: 587) |
| `SMTP_USER` | No | SMTP auth username |
| `SMTP_PASS` | No | SMTP auth password |
| `SMTP_SECURE` | No | Use TLS (default: true for port 465) |
| `NOTIFICATION_PROCESSOR_SECRET` | Yes | Secret for processing route auth |

Only provider-specific variables are required for the selected provider.

## Provider Acceptance vs Inbox Delivery

`sent` status means the provider accepted the message for delivery. It does NOT mean:
- The email reached the recipient's inbox
- The email was not bounced
- The email was opened or read

Provider webhooks for delivery status are out of scope for this milestone.

## Deferred Features (Not Implemented)

- SMS, WhatsApp, push notifications
- Marketing emails, newsletters
- Scheduled appointment reminders
- Follow-up messages, review requests
- Payment receipts, refund notifications
- Customer accounts, public cancellation/rescheduling links
- Calendar attachments (ICS), external calendar sync
- Provider delivery webhooks (bounce, delivered, opened, clicked)
- Bulk resend, notification campaigns
- Tenant-owned sending domains
- Email localization framework
